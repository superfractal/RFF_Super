# License and provenance review

**Review date:** 2026-09-24  
**Scope:** The tracked RFF_Super source and shader code, `extern/`, build and release scripts, website code, root `LICENSE`, `NOTICE`, `DISTRIBUTION.md`, and the verified release-candidate inventory and its bundled third-party notices/sources.

**Coverage note:** The tracked-path inventory contained 662 entries, 564 of them with source/build-code extensions. I ran repository-wide searches over the available code-bearing paths for license, copyright, attribution, source, and known third-party markers, then reviewed the identified implementations and license files. This is not a manual line-by-line review of every C++ file. The 16 tracked SPIR-V shader modules were disassembled to check their provenance as shader outputs, but the GLSL source is the basis of the algorithm review. Git-ignored scratch directories are outside the product-source conclusion.

## Assessment

I found **no confirmed license incompatibility or missing third-party license text in the tracked product source and reviewed dependency bundle**. The project has a detailed `NOTICE`, preserves the primary component licenses, and identifies most recognizable borrowed algorithms in both the notice and source comments.

There is one release-documentation item to resolve about the exact license options selected for static GMP, and the staged candidate is explicitly not approved for distribution. A few short published formulas have no express license statement at their cited source. I list those as low-risk provenance questions, not as established infringement.

This is a source and distribution review, not a legal opinion. Copyright and patent rules vary by jurisdiction and by product use.

## Items to resolve or preserve

### 1. Record the exact GMP and zstd license choices before release

`NOTICE` identifies GMP as LGPL-3.0-or-later **or** GPL-2.0-or-later, and zstd as BSD-3-Clause **or** GPL-2.0. `DISTRIBUTION.md` says static GMP is being used under GPLv3-compatible conditions, but does not state which GMP grant is selected for the distributed binary. Make that choice explicit in the release record. A simple record would be: GMP under GPL-2.0-or-later (the combined project is distributed under GPLv3), and zstd under BSD-3-Clause. If choosing GMP under LGPL-3.0-or-later instead, confirm and document the static-link compliance path, including users' ability to modify/recombine the application with a modified GMP library.

This is a clarity/compliance question, not evidence that the current build is incompatible. GMP publishes these alternatives in its [official copying terms](https://gmplib.org/manual/Copying); GNU's [license compatibility guidance](https://www.gnu.org/licenses/license-compatibility.en.html) and the [LGPLv3 text](https://www.gnu.org/licenses/lgpl-3.0.en.html) describe the relevant compatibility and combined-work conditions. The [zstd license](https://github.com/facebook/zstd/blob/dev/LICENSE) includes the BSD-3-Clause terms.

### 2. Keep the current release candidate blocked until the matching application source is supplied

`build/release-candidate-20260924-verified/DEPENDENCIES.json` is marked `INVENTORY_ONLY_NOT_A_RELEASE_APPROVAL`; the folder contains `NOT-FOR-DISTRIBUTION.txt`. Its third-party source/notice bundle is staged, but the matching RFF_Super source archive is not in that candidate. `DISTRIBUTION.md` already gives the correct next steps: build from a clean committed release tag, supply that tag's application source and build instructions with the binaries and third-party source bundle, then remove the marker only after the release checks pass.

This is a valid release gate, not a current license violation. Do not distribute the candidate folder as-is.

### 4. Standards and published shading equations

- **ITU-R BT.709 / BT.2020 / BT.2100:** `NOTICE:143-175` describes color primaries and transfer functions used in shaders and video export; I found no copied standards prose or figures in the code. Current editions are [BT.709-6](https://www.itu.int/rec/R-REC-BT.709), [BT.2020-2](https://www.itu.int/rec/R-REC-BT.2020), and [BT.2100-3](https://www.itu.int/rec/R-REC-BT.2100) (2025 for BT.2100). Keep the existing limitation to published parameters/functions and avoid reproducing standard text or tables. Adding exact edition numbers to the notice would improve auditability, but is not a license blocker. The [ITU-R patent information database](https://www.itu.int/en/ITU-R/study-groups/Pages/itu-r-patent-information.aspx) was not checked declaration-by-declaration; do that separately if making a product-conformance claim or if commercial patent clearance is required.
- **Studio GGX and clearcoat:** `shdsrc/studio_ggx.glsl:5-53` credits the GGX, correlated Smith, and Schlick references; `NOTICE:357-376` links the papers and Filament's Apache-2.0 documentation. The shader is identified as an independent implementation, and I found no copied Filament source code. No license issue is apparent. The named references include [Walter et al.](https://www.cs.cornell.edu/~srm/publications/EGSR07-btdf.pdf), [Heitz](https://jcgt.org/published/0003/02/03/), and [Filament's materials guide](https://google.github.io/filament/main/filament.html).
- **OpenStax thin-film reference:** `NOTICE:396-403` identifies the textbook as CC BY-NC-SA 4.0, while the shader independently evaluates refraction/optical path difference. I found no copied OpenStax prose, figures, or sample code. The textbook license therefore does not appear to attach to this implementation. Keep the source link and the independent-implementation note.

### 5. Make the IJG source terms traceable for `stb_image`

`extern/stb_image.c:675` and `:943` identify the JPEG inverse-DCT implementation as derived from IJG's `jidctint` / `DCT_ISLOW`. The [IJG README](https://github.com/libjpeg-turbo/ijg/blob/main/README) says its terms apply to software derived from IJG code and require the README to accompany source distributions, with changes to original files identified. The exact binary acknowledgement already appears in `NOTICE:54`, and the staged candidate contains `licenses/mingw-w64-x86_64-libjpeg-turbo/README.ijg`. However, the project source tree does not currently carry that README alongside `extern/stb_image.c`; a source-only archive generated directly from the repository could omit it. Before distributing source, include an unmodified copy of the applicable IJG README with the source bundle and explicitly map the `stb_image` IDCT derivation and adaptation in `NOTICE`/distribution notes. This is a **potential source-distribution compliance gap**, not a confirmed violation; if the IDCT is considered an independent implementation of the published algorithm rather than IJG-derived code, document that basis. The [upstream stb source](https://github.com/nothings/stb/blob/master/deprecated/stb_image.c) also marks the implementation public domain, but that statement does not remove terms that may apply to an embedded derived portion.

### 6. Record Abseil's embedded utility code in the nlohmann notice

`extern/nlohmann/json.hpp:3224-3264` explicitly says its C++11 `integer_sequence` fallback is taken from Abseil's `utility.h` and identifies Apache-2.0; it also retains the Abseil copyright marker. The full Apache-2.0 text is already present in root `LICENSE` for other dependencies, and I found no license incompatibility. `NOTICE:409-415` currently describes the header simply as MIT-licensed, though, and does not map this embedded Apache-licensed portion. Add an Abseil attribution/source pointer there so the notice accurately describes the single-header bundle. Compare the [official nlohmann v3.12.0 header](https://github.com/nlohmann/json/blob/v3.12.0/single_include/nlohmann/json.hpp) with the cited [Abseil source at the recorded commit](https://github.com/abseil/abseil-cpp/blob/10cb35e459f5ecca5b2ff107635da0bfa41011b4/absl/utility/utility.h); Abseil states its code is Apache-2.0 licensed ([license](https://github.com/abseil/abseil-cpp/blob/10cb35e459f5ecca5b2ff107635da0bfa41011b4/LICENSE)).

The same nlohmann header has a short `// boost::hash_combine` expression at `:6306-6311`. The source comment names Boost, and the project already includes the Boost Software License 1.0 text in `NOTICE`, but the notice currently lists only `src/vulkan_helper/hash/BoostHasher.hpp`. Add the nlohmann header path to that existing acknowledgement for a complete provenance trail. This is a low-risk, one-line formula issue, not an identified license conflict.

## Other reviewed components with no issue identified

- The application is GPL-3.0; the root `LICENSE` includes the relevant license texts. OpenCV 4.13 is Apache-2.0 and the notice explains its scope. Apache-2.0 is compatible with GPL-3.0; it would prevent relicensing this combined project under GPL-2.0-only, as reflected in GNU's [compatibility guidance](https://www.gnu.org/licenses/license-compatibility.en.html).
- The statically linked GMP and dynamically linked OpenCV/zstd dependency versions are recorded in the release inventory. The verified candidate includes the third-party source archives, patches, upstream license notices, and verification records for its reviewed dependency set.
- `extern/stb_image.c/.h` are version 1.33 and carry the upstream public-domain declaration ([upstream project](https://github.com/nothings/stb)); the IJG-derived IDCT source-distribution question is covered above. `extern/nlohmann/json.hpp` is v3.12.0 with its MIT license retained ([official release](https://github.com/nlohmann/json/releases/tag/v3.12.0)); its local SHA-256 matches the official release hash. Oklab source comments identify Ottosson and state the public-domain/MIT terms ([original article](https://bottosson.github.io/posts/oklab/)); Narkowicz's ACES curve code is offered under CC0 or MIT ([source](https://knarkowicz.wordpress.com/2016/01/06/aces-filmic-tone-mapping-curve/)). `lowbias32` is marked Unlicense, the Boost `hash_combine` acknowledgement includes the Boost Software License 1.0 text, and the selected Tailwind CSS v3 colors have source comments in each implementation file plus a NOTICE entry ([license](https://github.com/tailwindlabs/tailwindcss/blob/v3.4.17/LICENSE)).
- The website notice says its layout and scripts are independently authored. FFmpeg is launched as a user-supplied separate process and is not bundled; if an FFmpeg binary or codec is ever distributed, review its specific build configuration and codec/patent terms separately.
